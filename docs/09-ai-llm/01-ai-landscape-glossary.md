## 1. 为什么要学（和 Agent 有什么关系）

#### 为什么需要一张术语地图？

Agent 文档、SDK、论文摘要和同事聊天里，名词密度极高：

```text
「上下文爆了」——是字数爆了，还是 Token 爆了？窗口怎么计？
「我们微调一下」——真的要训权重，还是改 Prompt / 加 RAG？
「用 Completion 接口」——和 Chat messages 差在哪？Agent 该用哪个？
「上个 RAG」——是换更大模型，还是外挂检索？
「做成 Agent」——和「多轮 Chat」边界在哪？Tool 放哪一层？
```

名词不清时，讨论会变成各说各话；名词钉死后，才能正确选型和下刀。

#### 没有这张地图时，常见误会

| 口头说法 | 实际常指的是 | 错位后果 |
| --- | --- | --- |
| 「记忆不够」 | Context Window 满了 | 去找「永久记忆」产品，却不截断/摘要 |
| 「模型不懂我们公司」 | 缺领域知识进上下文 | 立刻上微调，忽略 RAG / 更好的 Prompt |
| 「再训一下」 | 其实想改 system 提示 | 浪费算力与周期 |
| 「Agent = 更聪明的 Chat」 | 缺工具循环与编排 | 只堆对话轮次，任务做不完 |

#### 本章要练的四种能力

1. **计量直觉**：用 Token / Context 解释计费、截断、为何要摘要
2. **阶段定位**：分清预训练 / 微调 / 推理，知道自己默认做推理
3. **接口形态**：Chat messages 是现代 Agent 的通信协议
4. **能力拼装**：Embedding → RAG → Tool → Agent 的层次关系

可以先记一句：

> 本章不是背词典，而是给后面每一章的 API、Prompt、RAG、Agent 装上同一套坐标系。

#### 前端 / 工程对照（先建立地图）

| 你熟悉的前端/后端概念 | 本章对应 |
| --- | --- |
| HTTP 请求体大小 / Header 限制 | Context Window（一次能塞多少） |
| CDN 缓存 / 搜索索引 | Embedding + 向量检索（RAG 的「外挂硬盘」） |
| 浏览器插件 / Node 调外部 API | Tool / Function Calling |
| 前端状态机 + 多步向导 | Agent 编排（规划 → 行动 → 观察 → 再规划） |
| `localStorage` 会话 vs 单次请求 payload | 「会话产品记忆」vs「单次请求上下文」 |
| 构建时打包 vs 运行时请求 | 预训练/微调（离线改模型）vs 推理（在线生成） |

## 2. 极简脉络（工程视角）

#### 为什么需要一条时间线？

不是为了背年代，而是知道：**你站在哪一层、哪些词属于哪一代问题**。  
「Attention 公式」和「怎么把 PDF 塞进 RAG」不是同一战场。

#### 怎么理解（一条工程向脉络）

```text
统计学习 / 深度学习
  → 表示学习与模型规模化
  → Transformer 成为主流骨架
  → 大规模预训练语言模型（LLM）
  → 对齐（指令跟随 / 对话）后成为 Chat 产品
  → 工具调用 + RAG + Agent 进入应用工程主战场
```

再压缩成你真正要站的位置：

```text
应用层工作流：

  API 调用
    → 编排（Prompt / messages / 工具循环）
    → 数据（语料、检索库、日志）
    → 评测（正确率、引用、延迟、成本）
    → 生产化（超时、重试、观测、权限、部署）
```

#### 示例：同一句话，不同年代的「解法」

任务：「根据公司内部制度回答员工请假天数」。

| 年代直觉 | 常见做法 | 你现在更该先想什么 |
| --- | --- | --- |
| 规则时代 | if/else + 关键词 | 规则脆、覆盖差 |
| 检索时代 | 搜文档再人工读 | 有材料，但没有生成层 |
| 纯 LLM 时代 | 把制度贴进 Prompt | Context 有限、更新麻烦 |
| RAG + Chat | 检索相关条款再生成 | **默认首选** |
| Agent | 再挂「查日历 / 提工单」工具 | 多步任务才需要 |

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 觉得必须先读完 Transformer 论文才能写 Agent | 进度卡住；工程主线其实是 API → 编排 → 数据 |
| 把「Chat 产品」和「LLM 底座」混为一谈 | 选型时只会比品牌，不懂对齐/上下文/工具能力 |
| 以为脉络终点是「更大模型」 | 应用瓶颈常在检索、工具、评测与成本，不在参数量口号 |

#### 工程对照

> **你要站的位置：应用层——API → 编排 → 数据 → 评测 → 生产化。**  
> 训练侧名词扫盲即可；把时间花在能交付的系统上。

## 3. 必掌握：LLM / Token / Context Window

这一节会刻意写细——后面每一章的计费、截断、Prompt 设计、Agent 记忆策略都建立在这三个词上。

### 3.1 LLM：大语言模型是什么

#### 为什么需要先钉死 LLM？

后面所有「聪明」「胡说」「会用工具」的讨论，默认主语都是它。定义模糊时，你会把产品包装和模型能力搅在一起。

#### 怎么理解

**LLM（Large Language Model）**：在大规模文本上训练出来的生成式模型。  
核心能力可以先记成一句：

> **根据已有上下文，预测下一个最合理的续写（token by token）。**

对齐（指令跟随 / 对话训练）之后，它在产品里表现为：聊天、写代码、总结、按格式输出、发起工具调用等——但底层仍是「条件生成」，不是数据库查询，也不是保证真相的搜索引擎。

心智图：

```text
输入上下文（Prompt / messages / 检索片段 / 工具结果）
        ↓
   LLM 逐 token 生成
        ↓
输出文本（或结构化字段 / tool_calls）
```

#### 示例：续写 vs「查事实」

```text
上下文：用户问「本公司年假是几天？」
若上下文里没有制度原文：
  → 模型仍可能「生成一段听起来像制度的话」
  → 这叫幻觉风险，不是「查库失败」

若上下文里有检索到的条款：
  → 模型更可能基于材料回答（仍需约束：要求引用、禁止编造）
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 把 LLM 当成精确数据库 | 数字、条款、人名容易一本正经胡说 |
| 以为「更大模型 = 自动有公司知识」 | 训练语料不含你的私有文档；要靠 RAG / 微调 / 工具 |
| 把 ChatGPT 产品功能全算进「模型本身」 | 联网、上传文件、记忆等常是产品层编排 |

#### 前端对照

| 前端直觉 | LLM |
| --- | --- |
| 组件根据 props/state 渲染 UI | 模型根据上下文生成下一 token |
| 没有数据时骨架屏/空态要设计 | 没有材料时要设计「拒答 / 要检索」策略 |
| 客户端状态 ≠ 服务端真相 | 模型输出 ≠ 权威事实 |

### 3.2 Token：模型读写的基本单位

#### 为什么需要 Token 这个概念？

计费、限速、上下文长度、截断策略，几乎都按 **token** 计，而不是按「字」或「英文单词」。  
搞不清 token，就无法估预算，也无法解释「为什么这段中文这么贵 / 这么占窗口」。

#### 怎么理解

Token 是分词器（tokenizer）切出来的片段，可能是：

- 一个英文单词或词根（`hello`、`ing`）
- 一个汉字、多个汉字，或汉字的一部分（**因模型而异**）
- 空格、标点、代码符号的特殊切法

关键结论：

> **Token ≠ 汉字一一对应，也 ≠ 英文单词一一对应。**

工程含义三条：

1. **计费**常按 input/output token（或合计）
2. **上下文长度**按 token 限制
3. **估算只能当数量级直觉**；唯一准绳是目标模型的 tokenizer，或响应里的 `usage`

#### 示例 / 对照（建立数量级，不要当公式）

下面数字是**教学用直觉**，真实值随 tokenizer 与文本内容剧烈变化：

| 文本类型 | 粗直觉 | 说明 |
| --- | --- | --- |
| 纯英文散文 | 约 1 token ≈ 0.75 词 量级 | 常见经验法则，非标准 |
| 中文 | 常常「同样信息量」比英文更吃 token | 不要用「1 字 = 1 token」 |
| 代码 | 括号、缩进、标识符可能切得很碎 | 贴大段代码特别吃窗口 |
| Base64 / 乱码式长串 | 可能异常膨胀 | 别把附件原文硬塞进 Prompt |

伪代码：看响应里的用量（下一章 API 会实战）：

```python
# 概念示意：真正字段名因厂商而异
usage = {
    "prompt_tokens": 1200,      # 输入
    "completion_tokens": 350,   # 输出
    "total_tokens": 1550,
}
# 账单与限流看的是这类数，不是 len(text)
```

中英文对照实验（同一语义，自己用任意在线 tokenizer 或 SDK 数一次更佳）：

```text
英文：How many annual leave days do employees get?
中文：员工年假有多少天？

→ 两个句子「意思接近」，token 数往往并不接近。
→ 结论：预算与截断策略必须按目标模型实测。
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 用字数 / 单词数估 token 做硬预算 | 上线后突然 413 / 爆窗 / 账单翻倍 |
| 以为所有模型同一套分词 | 换模型后同样 Prompt 占用可能变 | 
| 只盯输入、忽略输出 token | 让模型「长篇大论」时成本与延迟一起涨 |
| 把图片/文件「当文字长度」估 | 多模态计价与切分规则另一套，需看厂商文档 |

#### 工程对照

| 工程决策 | 和 Token 的关系 |
| --- | --- |
| 要不要把整份 PDF 贴进 Prompt | 直接决定是否爆窗与烧钱 |
| 日志是否全量记录 Prompt | 隐私与存储体积（按字符）vs 成本分析（按 token） |
| 流式输出 | 用户感知延迟 ↓，但 completion tokens 仍照计 |

### 3.3 Context Window：一次能「看见」多少

#### 为什么需要 Context Window？

模型并没有默认的「永久聊天记忆」。  
每一次推理，它只能看见**这次请求里放进上下文窗口的内容**（外加模型权重里学到的统计规律）。  
Agent 的「记忆」「多轮对话」「读了文档」——本质常常是：**你在窗口里塞了什么**。

#### 怎么理解

**Context Window（上下文窗口）**：单次请求中，模型能够作为条件看见的上下文上限。

计法因厂商而异，务必读文档：

| 计法 | 含义 | 工程影响 |
| --- | --- | --- |
| input + output **合计**不超过窗口 | 你写得越长，模型能答的空间越短 | 长历史 + 长回答更容易撞墙 |
| input / output **分项上限** | 输入、输出各自有 cap | 要分别规划 Prompt 与 `max_tokens` |

它**不是**：

- 会话永久记忆（产品层可以做记忆，但那是另存再取回）
- 「接了 RAG 就自动变 100 万窗口」（RAG 扩大的是**可检索资料规模**，每次仍只塞进片段）

爆窗常见后果：

```text
请求被拒绝 / 报错
自动截断（可能切掉最重要的 system 或工具结果）
质量明显下降（指示被挤掉、前后矛盾）
```

#### 示例：一次 Chat 请求里都占窗口

```text
system 提示（规则、人设、输出格式）
+ 少量 few-shot 示例
+ 检索到的 3 段制度原文（RAG）
+ 最近 N 轮 user/assistant 历史
+ 本轮 user 问题
+ （生成时）assistant 正在写出的 tokens
+ （工具场景）tool 返回的 JSON/文本
--------------------------------
全部挤在同一个 Context Window 里
```

伪占用账本（数字随意，重在结构）：

```text
system + 格式约束          800 tokens
RAG 三段引用              2200 tokens
最近 12 轮对话            3500 tokens
本轮问题                   120 tokens
预留输出                   800 tokens
--------------------------------
合计约                    7420 tokens
若窗口只有 8k → 已经危险
```

Agent 侧常见对策（后面章节会展开）：

1. **历史截断**：只留最近 K 轮，或按 token 预算裁剪
2. **摘要**：把旧对话压成短摘要再放回窗口
3. **RAG 精选**：只塞相关片段，不整库粘贴
4. **工具结果压缩**：表格/日志先摘要再回传
5. **分治**：长文档先大纲再按章问答，而不是一次塞完

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 把「产品里的聊天记录」当成模型自带记忆 | 换会话/换请求后模型「忘了」——其实你没把历史塞回去 |
| 以为 Context 越大就越该把什么都塞进去 | 噪声上升、成本上升、关键指令被稀释 |
| 忽略输出也占窗口（合计制） | 输入看似还行，一生成长文就爆 |
| 用 RAG「替代」窗口管理 | RAG 不检索时仍可能空；检索到的片段仍占窗口 |

#### 前端对照

| 前端 | Context Window |
| --- | --- |
| 一次 HTTP body 有大小限制 | 一次推理上下文有 token 上限 |
| Redux 全家桶不能无脑进每个请求 | 历史消息要筛选再发送 |
| 虚拟列表：数据很多，屏幕只渲染可见部分 | 知识库很大，每次只注入检索命中的片段 |
| Service Worker 缓存 ≠ 请求自动带上 | 外挂记忆必须显式读回并写入 Prompt |

一句话收束：

> **Token 决定怎么计量；Context Window 决定一次能带多少条件；Agent 工程大量工作是在「窗口预算」里做取舍。**

## 4. 必掌握：预训练 / 微调 / 推理

这一节会刻意写细——分清三阶段，才能判断「该调 API、该改 Prompt/RAG，还是真的要动权重」。

### 4.1 一张总表先建立坐标

| 阶段 | 英文 | 做什么 | 输入大致是什么 | 输出大致是什么 | 你常不常做 |
| --- | --- | --- | --- | --- | --- |
| 预训练 | Pretrain | 在海量数据上学语言与世界的统计规律 | 大规模通用语料 | 基座模型权重 | **很少**自己做 |
| 微调 | Finetune | 用领域/任务数据改行为或补知识 | 标注对话、领域文本、偏好数据等 | 适配后的权重（或 LoRA 等附件） | **有时** |
| 推理 | Inference | 用训练好的模型根据上下文生成 | Prompt / messages / 工具结果 | 文本、结构化输出、tool_calls | **天天做** |

时间线直觉：

```text
Pretrain（贵、慢、一次性大工程）
    ↓
（可选）SFT / 偏好优化 等对齐与微调
    ↓
部署成 API 或本地服务
    ↓
你的代码天天调用 = Inference
```

### 4.2 预训练（Pretrain）

#### 为什么需要了解它（即使你不做）？

因为它解释了：模型为什么「好像什么都懂一点」、为什么会有截止日期、为什么私有知识不会自动出现。

#### 怎么理解

预训练阶段，模型主要在学「下一个 token 怎么续」，从而内化语法、常识、代码风格、部分事实等**统计规律**。  
对应用开发者：

- 你买到/调用到的 Chat 模型，背后通常已经过预训练 + 对齐
- 你几乎不会从零预训练；成本与数据工程都不在 Agent 主线

#### 示例

```text
基座模型见过海量公开网页与书籍
  → 能写通顺中文、能解释「什么是 HTTP」
  → 但没见过你们公司 2024 版《请假制度.pdf》
  → 所以问内部制度时，不能指望「预训练已经学会」
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 以为调用 API 等于自己在预训练 | 你只是在消费已有权重做推理 |
| 用「再预训练一下」形容改 Prompt | 沟通成本爆炸，方案也会选错 |

### 4.3 微调（Finetune）与相关词

#### 为什么需要微调这个选项？

当「只靠 Prompt / RAG」仍稳定失败时——例如固定格式、行业口吻、特定任务策略——才考虑用领域数据改行为。  
但它**不是**注入私有知识的唯一手段，往往也不是第一选择。

#### 怎么理解

微调：在已有模型上，用你的数据继续训练，使输出分布更贴近目标任务。

常见相关词（扫盲级，能区分即可）：

| 名词 | 一句话 | 和你的关系 |
| --- | --- | --- |
| **SFT**（Supervised Fine-Tuning） | 用「输入→标准输出」对做监督微调 | 最常见的微调形态之一 |
| **RLHF / 偏好优化** | 用人类（或AI）偏好信号让回答更「顺眼/安全」 | 多由模型厂完成；你偶尔会在封闭数据上做类似事 |
| **Alignment（对齐）** | 让模型更听指令、更安全、更符合产品规范 | Chat 模型「能听话」很大程度靠它 |
| **LoRA 等参数高效微调** | 只训少量附加参数，降低成本 | 自托管场景更常见 |

#### 示例：该不该微调？

场景：客服机器人要回答「退货政策」。

| 方案 | 做法 | 何时更合适 |
| --- | --- | --- |
| Prompt | system 里写清语气与拒答规则 | 规则短、变化快 |
| RAG | 政策文档进向量库，检索后回答 | **知识常更新、要可追溯** |
| 微调 | 用大量历史工单对话训风格/流程 | 口吻与决策模式要「刻进模型」，且有数据与评测 |
| 工具 | 调订单 API 查物流状态 | 需要实时系统真相 |

多数企业内部知识问答：**先 RAG + Prompt，再评估要不要微调。**

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 知识一变就微调一版 | 迭代太慢；文档更新跟不上 |
| 没评测集就微调 | 「感觉更好」不可复现，还可能灾难性遗忘 |
| 把微调当成消除幻觉的银弹 | 仍可能编造；需拒答策略与引用约束 |

### 4.4 推理（Inference）：你天天做的事

#### 为什么这一节最重要？

因为 Agent 开发的默认日常就是：

> **调用已经对齐好的 Chat 模型 API，在上下文里完成生成（推理）。**

超时、重试、流式、token 预算、tool loop——全是推理期工程问题。

#### 怎么理解

推理 = 固定（或已加载的）权重 + 本次上下文 → 自回归生成输出。  
你写的 Python/TS 代码，几乎都活在这一层：

```text
拼 messages
  → POST /chat/completions（示意）
  → 拿回 assistant 文本或 tool_calls
  → 可能再调工具，把结果追加进 messages
  → 再推理……
```

#### 跑一下（概念级伪代码）

```python
# 这不是某一家 SDK 的真实 API，只演示「推理在干什么」
messages = [
    {"role": "system", "content": "你是简洁的中文助手。"},
    {"role": "user", "content": "用一句话解释什么是 Token。"},
]

# inference：远程或本地模型根据 messages 生成下一轮 assistant
response = llm.chat(messages)  # ← 你天天调用的就是这一步
print(response.content)
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 讨论方案时三阶段混用 | 「我们推理时微调一下温度」——词用错，协作混乱 |
| 以为 Temperature 属于预训练超参 | 它是**推理期采样**参数（见名词速查） |
| 忽略推理成本与延迟 | 每次 Agent 多一轮工具循环 = 多次推理账单 |

#### 工程对照：三阶段分别改什么

| 你想改变的行为 | 优先杠杆 | 阶段 |
| --- | --- | --- |
| 这次回答的格式/语气 | Prompt / messages | 推理 |
| 回答要依据最新内部文档 | RAG / 工具查库 | 推理 + 数据 |
| 稳定学会一种特殊决策风格 | 微调（需数据与评测） | 微调 |
| 从零创造一个基座模型 | 预训练 | 预训练（通常不是你） |

## 5. 必掌握：Chat vs Completion

这一节会刻意写细——现代 Agent 几乎都建立在 **Chat messages** 协议上；Completion 仍需认识，避免读旧文档时迷路。

### 5.1 两种形态对照

#### 为什么需要分清？

同一句「调用模型」，请求形状完全不同；工具调用、多轮历史、system 人设，都挂在 Chat 形态上。

| 维度 | Completion | Chat |
| --- | --- | --- |
| 形态 | 续写**一段文本** | **消息列表**（system / user / assistant / tool …） |
| 典型输入 | `prompt: "把 hello 翻译成中文："` | `messages: [{role, content}, ...]` |
| 现代 API | 仍存在，偏补全/旧代码 | **主流** |
| Agent | 少直接用 | 会话、工具循环都基于 messages |
| 多轮 | 自己把历史拼进一大段字符串 | 角色分离，结构清晰 |

### 5.2 Completion：续写一段话

#### 怎么理解

你给一段前缀，模型接着写。控制「谁在说话」往往要靠你在字符串里手写伪对话格式。

#### 示例：同一任务的 Completion 伪请求

任务：把 `hello` 译成中文。

```text
POST /v1/completions   （示意）
{
  "model": "some-completion-model",
  "prompt": "将下面英文翻译成中文，只输出译文。\nEnglish: hello\n中文：",
  "max_tokens": 32
}
```

模型可能续写出：`你好`

优点：简单、适合「补全到某个停止符」。  
缺点：多轮、工具、系统指令混在一个大字符串里，易乱、难维护。

### 5.3 Chat：消息列表才是现代默认

#### 怎么理解

Chat API 把对话拆成带 **role** 的消息，模型在「对话上下文」上生成下一轮 assistant（或 tool_calls）。

消息角色直觉：

```text
system     设定规则与人设（通常最稳、最优先遵守的那层）
user       用户输入
assistant  模型回复（也可在 few-shot 里充当「示范回答」）
tool       工具结果回传（工具调用场景；名称因厂商而异）
```

#### 示例：同一任务的 Chat 伪请求

```text
POST /v1/chat/completions   （示意）
{
  "model": "some-chat-model",
  "messages": [
    {"role": "system", "content": "你是翻译官。只输出译文，不要解释。"},
    {"role": "user", "content": "hello"}
  ]
}
```

多轮时自然生长：

```text
messages = [
  system,
  user1, assistant1,
  user2, assistant2,
  user3          ← 本轮问题
]
```

工具循环时再插入（概念）：

```text
user → assistant(tool_calls) → tool(结果) → assistant(最终回答)
```

这正是 Agent 编排的通信骨架（后续模块会展开）。

### 5.4 对照示例：为什么 Agent 选 Chat

#### 示例：带规则的多轮

Completion 容易变成：

```text
### System
你是客服……
### User
我的订单呢？
### Assistant
请提供订单号。
### User
A10086
### Assistant
……（你必须自己维护这套标记，还要防模型学歪格式）
```

Chat 则是结构化列表，SDK/服务端按角色处理；再叠加 `tool` 角色后，Function Calling 才好落地。

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 在 Chat 模型上仍把一切糊成一个 user 大字符串 | 失去 system/few-shot/tool 的结构优势 |
| 以为 system 只是「注释」 | 它是默认的高优先级行为约束（仍非数学保证） |
| 把「产品 UI 的聊天气泡」等同于 API messages | UI 可省略 system；真正请求里通常仍要带规则 |
| 新旧文档混读，拿 Completion 示例硬套 Chat SDK | 字段对不上，调试浪费时间 |

#### 前端对照

| 前端 | Chat messages |
| --- | --- |
| 聊天 UI 的 message list | API 的 `messages[]` |
| 系统通知 / 配置 | `system`（不一定展示给用户） |
| 调用后端再展示结果 | `assistant` 发起 `tool`，前端/后端执行后回填 |
| 不可变更新 append 一条消息 | Agent 每轮把新消息 append 再请求 |

## 6. 建议掌握：RAG / Agent / Tool / Embedding 总览

这一节会刻意写细——四者常被混称「AI 应用」；画不清关系，就不知道缺的是检索、工具，还是编排。

### 6.1 四个词各是什么

#### 为什么需要总览？

后面模块会分别深挖；本章先建立**可画在一张纸上的地图**，避免学 RAG 时以为自己在做 Agent，或做 Agent 时忘记检索。

#### 怎么理解（先记四句）

```text
Embedding：文本 → 向量，用于相似度检索（等任务）
RAG：     先检索知识，再让 LLM 基于材料生成
Tool：    模型可调用的外部能力（搜索、DB、代码、邮件…）
Agent：   模型 + 记忆/规划 + 工具循环，完成多步任务
```

关系总图：

```text
                 ┌─────────────┐
                 │  Chat LLM   │  ← 引擎（推理）
                 └──────┬──────┘
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │   RAG    │  │   Tool   │  │  Memory  │
   │(外挂知识)│  │(行动能力)│  │(摘要/库) │
   └────┬─────┘  └────┬─────┘  └──────────┘
        │             │
        ▼             │
   Embedding          │
   + 向量库/检索      │
                      ▼
              ┌───────────────┐
              │     Agent     │  ← 编排上述能力的系统
              └───────────────┘
```

再记一句分层：

> **Chat LLM 是引擎；RAG 给它外挂知识；Tool 给它行动能力；Agent 是编排这些能力的系统。**

### 6.2 Embedding：文本变成可计算的向量

#### 为什么需要？

计算机不好直接对「语义相近」做匹配。Embedding 把一段文本打成向量，使「相近意思」在向量空间里距离更近，从而支持检索。

#### 怎么理解

```text
"年假有多少天？"     →  [0.12, -0.44, ...]
"员工可休几天年假？" →  [0.11, -0.43, ...]   ← 距离近
"如何重启路由器？"   →  [-0.87, 0.20, ...]  ← 距离远
```

注意：Embedding 模型通常**不是**你对话用的那个大 Chat 模型（可以是专门的小模型/API）。

#### 示例：检索候选

```text
查询：年假天数
库中文档块：
  1. 年假制度第 3 条……（高相似）
  2. 报销发票要求……（低相似）
  3. 路由器故障排查……（低相似）
→ 取 Top-K 片段交给 RAG
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 以为 Embedding 会「回答问题」 | 它主要负责表示与检索，不负责最终答复 |
| 混用不同 Embedding 模型的向量 | 空间不一致，相似度无意义 |
| 把整本书做成一个向量 | 粒度太粗，检索不准（通常要切块） |

### 6.3 RAG：检索增强生成

#### 为什么需要 RAG？

LLM 窗口有限、私有知识不在权重里、事实还要可更新可追溯。  
RAG 的套路是：**先找材料，再让模型基于材料说**。

#### 怎么理解

```text
用户问题
  →（可选）改写查询
  → Embedding + 检索 Top-K 文档块
  → 把文档块 + 问题拼进 Prompt / messages
  → LLM 生成答案（最好要求引用）
```

和「把整库塞进 Context」的区别：

| 做法 | 知识规模 | 每次窗口占用 | 更新成本 |
| --- | --- | --- | --- |
| 全量粘贴 | 受窗口死死限制 | 极大 | 改 Prompt |
| RAG | 库可很大 | 只占 Top-K | 更新索引/文档 |

#### 示例：有无 RAG 的回答差异

```text
问：试用期能否请年假？

无 RAG：模型可能按「通用劳动法印象」编一条（风险高）
有 RAG：Prompt 中含《员工手册》§4.2 原文 → 要求必须依据原文，找不到就说不知道
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 检索很差却怪模型笨 | 垃圾进、垃圾出；先查召回 |
| 检索很多段却不标来源 | 无法审计，幻觉更难发现 |
| 以为上了 RAG 就不会胡说 | 模型仍可能忽略材料；需要指令与校验 |

### 6.4 Tool：模型的「手」

#### 为什么需要 Tool？

纯文本生成拿不到实时系统状态，也不能真的下单、查库、跑代码。  
Tool（及 Function Calling）让模型在对话中**结构化地请求外部能力**，由你的代码执行后再把结果喂回模型。

#### 怎么理解

```text
用户：我的订单 A10086 到哪了？
助手（模型）：发起 tool_call → get_order(id="A10086")
你的后端：查 DB / 调快递 API → 返回 JSON
助手（模型）：基于 JSON 生成自然语言答复
```

Tool 可以是：搜索、SQL、HTTP、日历、代码解释器、发送邮件……  
**危险操作必须有权限与确认**——这是工程问题，不是模型自觉。

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 让模型「直接拥有」数据库账号在 Prompt 里 | 安全事故；应走受控工具层 |
| 工具返回数兆日志原文 | 立刻打爆 Context |
| 把 Tool 和 RAG 对立 | 常组合：RAG 查知识，Tool 查实时态 |

### 6.5 Agent：编排起来的多步系统

#### 为什么需要 Agent 这个词？

当任务需要「多步决策 + 观察环境 + 再行动」时，单次 Chat 不够。  
Agent ≈ 在循环里使用 LLM：规划、选工具、读结果、更新记忆、直到结束。

#### 怎么理解

最小循环（概念）：

```text
while 未完成 and 未超步数:
    LLM 看当前 messages / 状态
    → 决定：回答用户 / 调用工具 / 再检索
    → 执行行动，把观察写回上下文
```

和「多轮 Chat」的差别：

| | 多轮 Chat | Agent |
| --- | --- | --- |
| 驱动 | 主要等人接着问 | 系统可在中间自主多步 |
| 工具 | 可有可无 | 常常是核心 |
| 失败恢复 | 用户重试 | 需步数上限、超时、重试与人工接管 |
| 状态 | 聊天历史 | 历史 + 任务状态机 / 记忆 / 计划 |

#### 示例：同一需求的四种落点

需求：「根据制度回答年假，并帮我提交请假单。」

```text
仅 Chat：只能聊天解释，不能提交
Chat + RAG：能依据制度解释，仍不能提交
Chat + Tool：能提交，但可能引用错制度
Agent = Chat LLM + RAG + Tool + 编排循环：
  先检索制度 → 确认天数 → 调提交接口 → 把单号回复用户
```

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 把任何 Chatbot 都叫 Agent | 概念通胀；无法讨论要不要状态机/工具 |
| 无步数/无超时的工具循环 | 死循环烧钱，或卡死请求 |
| 一上来就上复杂多智能体 | 先把单 Agent + 好工具 + 好检索做稳 |

#### 前端 / 工程对照

| 前端/后端 | AI 侧 |
| --- | --- |
| 搜索服务 + 结果页摘要 | Embedding + RAG |
| BFF 聚合多个 API | Tool 编排 |
| 向导式表单状态机 | Agent 任务状态 |
| 乐观 UI + 失败回滚 | 工具调用的确认与补偿 |

## 7. 建议掌握：开源 vs 闭源格局（认知级）

#### 为什么需要格局直觉？

选型争论容易变成品牌站队。工程上更有用的是：**数据是否出域、要不要自运维、迭代速度、能否换模型**。

#### 怎么理解

| 类型 | 特点 | 选用直觉 |
| --- | --- | --- |
| 闭源 API | 能力强、省运维、生态工具多；数据出域需评估 | 快速做产品 / MVP |
| 开源可自托管 | 可控、可私有化；要算力、运维、评测与安全加固 | 强合规、内网、深度定制 |

没有永远的「第一」。能力榜单会变；你的系统却要活几年。

#### 示例：两道选型题（练习里也会做）

**创业 MVP（对外演示、要速度）**

- 倾向：闭源 API + 薄适配层
- 理由示例：上线快、少运维、先验证需求；用环境变量换模型；核心业务数据尽量少上传

**强合规内网（代码与文档不出域）**

- 倾向：开源/商业可私有化部署 + 内网推理
- 理由示例：数据不出域；可审计；成本在规模化后可测算；代价是 GPU/运维与效果调参

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| SDK 调用写死某一家特有字段满地 | 换模型时重写整站 |
| 只比「智商榜」忽略延迟/价格/限流 | 演示很猛，账单与超时很崩 |
| 忽视日志里的 Prompt 也是敏感数据 | 合规漏洞 |

#### 工程建议

> 做 **适配层**（统一的 `chat()` / `embed()` 接口），业务只依赖你的抽象，不依赖某一家 SDK 细节。  
> 下一章开始写 API 封装时就会落到代码里。

## 8. 了解即可：训练与论文脉络

#### 为什么单独开一节「了解即可」？

避免两种极端：要么被论文吓退，要么觉得必须先当研究员。  
这些词出现时你能点头，并知道**不影响先做出 Agent**。

#### 扫盲地图（不展开公式）

| 主题 | 一句话 | 和你的关系 |
| --- | --- | --- |
| Attention / Transformer | 主流骨架，让长程依赖与并行训练更可行 | 知道 Chat 模型多基于此即可 |
| 缩放定律（Scaling Laws） | 数据/参数/算力上去，能力常随之涨（有条件） | 解释「为何大家都堆规模」 |
| MoE | 稀疏激活专家混合，常用于做大而不线性加推理成本 | 见到型号带 MoE 不慌 |
| 并行训练（数据/张量/流水线并行） | 大模型怎么在多卡上训得动 | 运维/训练岗才深挖 |
| 评测基准（MMLU 等） | 公开题库上的分数 | **不能替代**你的业务评测集 |

#### 易错点

| 错法 | 会发生什么 |
| --- | --- |
| 读论文替代做评测与日志 | 业务仍不达标 |
| 用基准分数直接当选型唯一依据 | 忽略中文、工具、延迟、领域数据 |

感兴趣再读；主线请回到 API、Prompt、RAG、Agent。

## 9. 名词速查（常挂嘴边）

| 名词 | 一句话 | 何时会碰到 |
| --- | --- | --- |
| Hallucination（幻觉） | 一本正经胡说：流畅但不真 | 无依据问答、数字与条款 |
| Temperature | 采样随机性：低更稳，高更活（也更飘） | 调创造性 vs 确定性 |
| Top-p（核采样） | 另一类多样性控制，与 temperature 常需协调 | 采样参数调优 |
| Latency | 延迟：首 token / 整段完成时间 | 流式、超时、体验 |
| Throughput | 吞吐：单位时间处理量 | 批处理、限流、容量规划 |
| Function / Tool Calling | 模型结构化提出工具调用，由系统执行 | Agent 行动 |
| Multimodal（多模态） | 不止文本：图、音、视频等 | 读图、单据识别等 |
| Guardrails（护栏） | 输入输出安全与合规拦截 | 防注入、防越权、敏感内容 |
| Tokenizer | 文本 ↔ token 的分词器 | 估长度、排爆窗 |
| System Prompt | 系统侧规则与人设消息 | 行为约束、格式要求 |
| Few-shot | 在上下文里给少量示例 | 教格式/风格 |
| Grounding | 让回答锚定到检索/工具等外部依据 | RAG 设计目标之一 |

闪卡提示（对应练习 C1）：正面写名词，背面用「一句话 + 一个你自己的例子」。
