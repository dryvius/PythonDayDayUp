## 1. 为什么选 PostgreSQL

上一章用 SQLite 练 SQL 语法；本章把「生产里真正常见」的那一侧补齐。

#### 为什么需要单独学 PG？

SQLite 很好：零部署、文件即库、练 CRUD/JOIN 够用。但 Agent 服务一上线，你会立刻碰到 SQLite 不擅长的事：

| 场景 | SQLite 的现实 | PG 更常见的做法 |
|------|---------------|-----------------|
| 多进程 / 多副本写同一库 | 写锁、部署麻烦 | 客户端-服务端，多连接并发 |
| 半结构化扩展字段 | 有 JSON，能力偏基础 | **JSONB** + 运算符/索引 |
| 全文检索、向量检索 | 要另找方案 | 扩展生态（含向量相关扩展） |
| 教程与云托管 | 偏本地玩具 | FastAPI / SQLAlchemy / RDS 大量以 PG 为例 |

可以先记一句：

> SQLite 练语法；PostgreSQL 练「能上线的数据层直觉」。

#### 怎么选（和常见替代对照）

不必背品牌榜，先会回答「为什么我们默认 PG」：

| 选项 | 适合 | 本章态度 |
|------|------|----------|
| **PostgreSQL** | 通用 OLTP、JSON、扩展、云托管成熟 | **主线** |
| SQLite | 单机、嵌入、练习、小型工具 | 语法练手保留 |
| MySQL / MariaDB | 大量存量业务 | 知道存在；类型/方言细节不同 |
| 纯文档库（Mongo 等） | 文档为主、弱事务关联 | Agent 里「会话+消息」仍常要关系约束 |

选 PG 的几条硬理由（写进笔记即可）：

1. **可靠 + SQL 标准好**：约束、事务、类型系统扎实  
2. **JSONB、全文检索、扩展**（含向量相关扩展生态）对 AI / Agent 应用友好  
3. **生态强**：FastAPI / SQLAlchemy 教程大量以 PG 为例；云厂商托管一键可得  

#### 跑一下（先建立「服务」心智，不必装齐全家桶）

即使这会儿还没起容器，也能先在脑子里画清三角关系：

```text
你的 Python 进程
    │  TCP 连接（默认 5432）
    ▼
PostgreSQL 服务（容器 / 本机 / 云）
    │
    ▼
数据文件 + WAL（崩溃可恢复）
```

和 SQLite「打开一个 `.db` 文件」不同：**先有服务，再有连接串**。

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 以为「会写 SQLite SQL = 会用 PG」 | 类型名、自增、`TRUE/FALSE`、时区时间等细节会绊倒 |
| 本地一直用 SQLite，生产突然换 PG | 迁移脚本、类型映射、连接池一次爆出来 |
| 为了「简单」跳过约束 | 脏 `role`、孤儿消息、重复 email 进库后难清 |

#### SQLite 对照

| 点 | SQLite | PostgreSQL |
|----|--------|------------|
| 部署 | 一个文件 | 独立服务 + 端口 |
| 类型 | 更松（亲和类型） | 更严（声明什么存什么） |
| 布尔 | 常用 `0/1` | 原生 `BOOLEAN` |
| JSON | `JSON1` | **JSONB**（二进制、可索引） |
| 自增 | `INTEGER PRIMARY KEY` | 常 `BIGSERIAL` / `GENERATED` / `UUID` |

## 2. 必掌握：常用类型

这一节会刻意写细——建表时类型选错，后面 ORM、迁移、索引都会跟着疼。

### 2.1 选型总表（先建立地图）

#### 为什么先看表？

Agent 表字段高度重复：id、用户、正文、时间、扩展元数据。先把「常用武器」认全，再逐个踩坑。

| 类型 | 用途 | Agent 里常见字段 |
|------|------|------------------|
| `BOOLEAN` | 开关 | `is_archived`、`is_deleted` |
| `INTEGER` / `BIGINT` | 整数 id、计数 | 自增主键、token 计数 |
| `TEXT` / `VARCHAR` | 字符串 | `user_id`、`title`、`role` |
| `TIMESTAMPTZ` | **带时区**时间（推荐） | `created_at`、`updated_at` |
| `UUID` | 分布式 id | `session_id`、跨服务关联 |
| `JSONB` | 半结构化 JSON（建议掌握） | `metadata`、工具参数快照 |
| `NUMERIC` | 精确小数 | 金额、计费单价（别用浮点） |

#### 怎么写（Agent 会话表示例）

```sql
CREATE TABLE chat_sessions (
  id UUID PRIMARY KEY,
  user_id TEXT NOT NULL,
  title TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

读字段：

| 列 | 类型选择理由 |
|----|--------------|
| `id` | 会话常跨服务引用 → `UUID` |
| `user_id` | 可能来自 Auth 的字符串 id → `TEXT` |
| `title` | 可空标题 → `TEXT` |
| `created_at` | 要可排序、可跨时区对比 → `TIMESTAMPTZ` + `DEFAULT now()` |

### 2.2 `TEXT` / `VARCHAR` / 字符串习惯

#### 为什么纠结字符串类型？

很多人从 MySQL 惯性带来「必须 `VARCHAR(255)`」。在 PG 里，**多数业务字符串直接用 `TEXT` 就够**。

#### 怎么写

```sql
-- 推荐：无硬长度上限的业务字符串
user_id TEXT NOT NULL,
title TEXT,

-- 真有协议长度时再用 VARCHAR
country_code VARCHAR(2)
```

#### 跑一下

```sql
CREATE TABLE demo_str (
  a TEXT,
  b VARCHAR(5)
);

INSERT INTO demo_str (a, b) VALUES ('hello-world', 'ok');
-- 下面会失败：b 超长
-- INSERT INTO demo_str (a, b) VALUES ('x', 'too-long');
```

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 无脑 `VARCHAR(255)` 一切 | 能跑，但截断风险 / 无意义限制；PG 里通常不如 `TEXT` 清晰 |
| 用字符串存「像枚举」却不加 `CHECK` | `'User'` / `'user'` / `'USER'` 三种脏数据并存 |
| 把超大正文塞进每行又从不归档 | 表膨胀；正文仍可用 `TEXT`，但要想生命周期 |

#### 对照

| 需求 | 倾向 |
|------|------|
| 无固定上限（消息正文、标题） | `TEXT` |
| 协议固定短码（国家码、币种） | `VARCHAR(n)` 或 `CHAR(n)` |
| 取值集合封闭（role） | `TEXT` + `CHECK`，或后续枚举类型 |

### 2.3 整数：`INTEGER` / `BIGINT` / `BIGSERIAL`

#### 为什么分这么细？

id 与计数看起来都是「数字」，溢出和自增策略不同。

#### 怎么写

```sql
CREATE TABLE messages (
  id BIGSERIAL PRIMARY KEY,          -- 自增 BIGINT
  token_count INTEGER,               -- 一般计数够用
  session_id UUID NOT NULL
);
```

| 写法 | 含义 |
|------|------|
| `INTEGER` | 4 字节整数 |
| `BIGINT` | 8 字节；大数据量主键更常见 |
| `BIGSERIAL` | 近似「`BIGINT` + 序列默认值」的便捷写法 |
| `GENERATED BY DEFAULT AS IDENTITY` | SQL 标准身份列（新项目也可选） |

#### 跑一下

```sql
CREATE TABLE demo_serial (
  id BIGSERIAL PRIMARY KEY,
  label TEXT NOT NULL
);

INSERT INTO demo_serial (label) VALUES ('a'), ('b');
SELECT * FROM demo_serial;
-- id 自动变成 1, 2
```

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 高并发插入却用小范围类型硬撑 | 远期溢出（少见但疼） |
| 把「业务编号」和「代理主键」搅在一起 | 改号策略困难；代理键用序列/UUID，业务键另列 |
| 在应用里自己拼最大 id+1 | 竞态；用序列 / UUID |

### 2.4 时间：为什么强烈推荐 `TIMESTAMPTZ`

#### 为什么这一点是必掌握？

Agent 日志、会话排序、计费窗口全靠时间。用错类型，夏令时/跨时区一查就乱。

| 类型 | 存的是什么 | 本章建议 |
|------|------------|----------|
| `TIMESTAMP` | **无时区**时间戳 | 慎用 |
| `TIMESTAMPTZ` | 存 UTC 瞬间，按会话时区显示 | **推荐** |
| `DATE` | 只有日期 | 生日、营业日等 |

#### 怎么写

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_at TIMESTAMPTZ
```

应用侧原则：

1. 库内统一按「瞬间」存（`TIMESTAMPTZ`）  
2. 展示时再转到用户时区  
3. API 交换优先 ISO8601（带 `Z` 或偏移）

#### 跑一下

```sql
CREATE TABLE demo_ts (
  id BIGSERIAL PRIMARY KEY,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

INSERT INTO demo_ts DEFAULT VALUES;
SELECT id, created_at, created_at AT TIME ZONE 'Asia/Shanghai' AS local_cn
FROM demo_ts;
```

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 用 `TEXT` 存时间字符串 | 不能正确排序/比较；索引与函数都别扭 |
| 混用 `TIMESTAMP` 与 `TIMESTAMPTZ` | 隐式转换，排障极痛 |
| 应用写本地时间却当 UTC | 差 8 小时的经典事故 |

#### SQLite 对照

上一章 SQLite 示例常用 `TEXT` 存 ISO 字符串——练习可以。**PG 生产表请用 `TIMESTAMPTZ`。**

### 2.5 `UUID`：分布式 id

#### 为什么 Agent 爱用 UUID？

会话 id 常被 URL、前端、多个服务引用；若用自增整数：

- 未插入前拿不到稳定 id（或要先 insert）  
- 多库合并、导入导出易撞号  
- 从 id 可猜测业务量（信息泄露）

UUID 换来：应用层可先生成再插入。

#### 怎么写

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;  -- 若用 gen_random_uuid()；PG13+ 常已内置

CREATE TABLE chat_sessions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

应用层也可自己生成（Python `uuid.uuid4()`）再插入——两边选一种团队约定即可。

#### 跑一下

```sql
INSERT INTO chat_sessions (user_id) VALUES ('u-42') RETURNING id, created_at;
```

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| UUID 当字符串乱比大小当「时间序」 | UUID4 无序；要时间序看 `created_at` 或用时间有序 id 方案 |
| 主键用 UUID 却完全不建其它查询索引 | 按 `user_id` 查会话仍然慢 |
| 文档写 UUID、库里却是 `TEXT` | 校验与存储浪费；类型不一致 |

#### 对照：UUID vs BIGSERIAL

| | UUID | BIGSERIAL |
|--|------|-----------|
| 生成位置 | 应用或数据库 | 主要在库内序列 |
| 可读性 | 差 | 好 |
| 多服务合并 | 友好 | 要协调 |
| 索引局部性 | UUID4 较碎 | 更紧凑 |

挑战题会让你写优劣——上表够用。

### 2.6 `BOOLEAN` / `NUMERIC` / `JSONB`（地图）

#### 为什么这三个常一起出现？

- `BOOLEAN`：软删除、归档开关  
- `NUMERIC`：钱与精确小数（**不要**用 `FLOAT`/`DOUBLE` 存钱）  
- `JSONB`：扩展字段（第 6 节展开）

#### 怎么写

```sql
is_archived BOOLEAN NOT NULL DEFAULT FALSE,
price NUMERIC(12, 2),          -- 精确到分
metadata JSONB NOT NULL DEFAULT '{}'::jsonb
```

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 用 `FLOAT` 存金额 | `0.1 + 0.2` 类误差进账本 |
| `BOOLEAN` 用 `NULL` 表示第三态却不解释 | 查询要写 `IS TRUE`；团队约定「禁止 NULL」更简单 |
| 核心筛选字段只放在 JSONB 里 | 能查，但索引与约束都变难（见 §6） |

## 3. 必掌握：约束

类型决定「格子长什么样」；约束决定「脏数据进不进得来」。

### 3.1 五类约束地图

#### 为什么约束是必掌握？

Agent 最怕的不是查得慢，而是：

- 同一 email 两行用户  
- `messages.session_id` 指向不存在的会话  
- `role = 'User'` 大小写乱飞导致统计错误  

约束把这些问题挡在写入期。

| 约束 | 作用 | 一句话 |
|------|------|--------|
| `PRIMARY KEY` | 唯一标识一行 | 表的身份证 |
| `FOREIGN KEY` | 引用完整性 | 子行必须有父行 |
| `UNIQUE` | 某列/组合唯一 | email、业务键 |
| `NOT NULL` | 非空 | 关键路径不许缺 |
| `CHECK` | 取值检查 | 枚举式合法值 |

### 3.2 怎么写：会话 + 消息（完整示例）

```sql
CREATE TABLE chat_sessions (
  id UUID PRIMARY KEY,
  user_id TEXT NOT NULL,
  title TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE messages (
  id BIGSERIAL PRIMARY KEY,
  session_id UUID NOT NULL REFERENCES chat_sessions(id),
  role TEXT NOT NULL CHECK (role IN ('system', 'user', 'assistant', 'tool')),
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 假设另有 users 表时：
-- CREATE UNIQUE INDEX uniq_users_email ON users(email);
```

拆开看 `messages`：

| 片段 | 含义 |
|------|------|
| `BIGSERIAL PRIMARY KEY` | 代理主键 + 自增 |
| `REFERENCES chat_sessions(id)` | 外键：会话必须先存在 |
| `CHECK (role IN (...))` | 角色白名单 |
| `content TEXT NOT NULL` | 不允许空正文 |

### 3.3 跑一下

在已连接的库里依次执行（可先 `DROP TABLE IF EXISTS messages, chat_sessions;`）：

```sql
INSERT INTO chat_sessions (id, user_id, title)
VALUES ('11111111-1111-1111-1111-111111111111', 'u-1', 'demo');

INSERT INTO messages (session_id, role, content)
VALUES ('11111111-1111-1111-1111-111111111111', 'user', 'hello');

-- 应失败：非法 role
-- INSERT INTO messages (session_id, role, content)
-- VALUES ('11111111-1111-1111-1111-111111111111', 'User', 'hi');

-- 应失败：会话不存在
-- INSERT INTO messages (session_id, role, content)
-- VALUES ('22222222-2222-2222-2222-222222222222', 'user', 'orphan');
```

成功时：

```sql
SELECT m.id, m.role, m.content, s.user_id
FROM messages m
JOIN chat_sessions s ON s.id = m.session_id;
```

### 3.4 外键删除策略（知道选项即可）

#### 为什么要提？

删会话时，消息怎么办？默认外键会**拒绝删除父行**（保护你）。

```sql
-- 示例：级联删除消息（是否采用看产品；多数 Agent 偏好软删除）
session_id UUID NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE
```

| 策略 | 行为 |
|------|------|
| 默认（NO ACTION / RESTRICT） | 有子行则删父失败 |
| `ON DELETE CASCADE` | 删父连带删子 |
| `ON DELETE SET NULL` | 子外键置空（列需可空） |

Agent 实务更常见：**软删除**（`deleted_at`）而不是物理级联删。

### 3.5 `UNIQUE`：约束 vs 唯一索引

#### 怎么写

```sql
-- 表内约束
email TEXT NOT NULL UNIQUE,

-- 或独立唯一索引（等价常见写法，便于命名）
CREATE UNIQUE INDEX uniq_users_email ON users(email);
```

两者都阻止重复；索引额外服务查找。教学上记住：**要唯一，就显式建 UNIQUE**。

### 3.6 易错点

| 错法 | 会发生什么 |
|------|------------|
| 只在应用层校验 role | 另一条写入路径绕过 → 脏数据 |
| 外键类型与父主键类型不一致 | 建不成或隐式转换陷阱 |
| 唯一约束漏了 `NULL` 语义 | PG 里多个 `NULL` 通常不互相冲突（`UNIQUE` 允许多个 NULL） |
| 生产表无 FK「图省事」 | 孤儿行；JOIN 统计失真 |

### 3.7 对照：约束 vs 应用校验

| 层 | 做什么 |
|----|--------|
| Pydantic / 业务代码 | 友好错误信息、权限、复杂规则 |
| 数据库约束 | **最后防线**；多客户端/脚本/任务写入也生效 |

两边都要；不要互相替代。

## 4. 必掌握：本地 / 容器启动

目标：你的机器上有一个可连的 Postgres，并拿到连接串。

### 4.1 为什么优先 Docker？

| 方式 | 优点 | 缺点 |
|------|------|------|
| Docker 官方镜像 | 版本固定、可丢可重建、和队友一致 | 需安装 Docker |
| 本机安装包 | 无容器依赖 | 版本漂移、卸载残留 |
| 云托管开发实例 | 接近生产 | 网络/费用/延迟 |

课程默认：**Docker 起一个可扔的库**。

### 4.2 怎么写：一条 `docker run`

```bash
docker run --name pg-agent \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=agent \
  -p 5432:5432 \
  -d postgres:16
```

参数直觉：

| 片段 | 含义 |
|------|------|
| `--name pg-agent` | 容器名，方便 `docker stop/start` |
| `POSTGRES_PASSWORD` | 超级用户 `postgres` 的密码（**仅本地演示**） |
| `POSTGRES_DB=agent` | 自动创建数据库名 `agent` |
| `-p 5432:5432` | 宿主机 5432 → 容器 5432 |
| `-d` | 后台跑 |
| `postgres:16` | 大版本钉死，避免「我机器上是 14」纠纷 |

连接串直觉：

```text
postgresql://postgres:postgres@localhost:5432/agent
```

拆开：

```text
postgresql:// 用户:密码 @ 主机:端口 / 数据库名
```

### 4.3 跑一下：确认活着并连上

```bash
# 容器是否在跑
docker ps

# 看日志（启动完成前可能短暂拒绝连接）
docker logs pg-agent

# 用官方客户端进库（容器内 psql）
docker exec -it pg-agent psql -U postgres -d agent
```

在 `psql` 里：

```sql
SELECT version();
\dt
\q
```

客户端选项（任选其一即可）：

| 客户端 | 用途 |
|--------|------|
| `psql`（CLI） | 脚本、排障、和文档一致 |
| DBeaver / 其它 GUI | 看表、点查询 |
| Python 驱动 | 下一节 / 下一章 |

### 4.4 可选：`docker compose` 固定下来

项目里更常见用 compose，避免每次记长命令：

```yaml
# docker-compose.yml（示例）
services:
  db:
    image: postgres:16
    container_name: pg-agent
    environment:
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: agent
    ports:
      - "5432:5432"
    volumes:
      - pg_agent_data:/var/lib/postgresql/data

volumes:
  pg_agent_data:
```

```bash
docker compose up -d
docker compose down          # 停
# docker compose down -v    # 停并删卷（数据没）——慎用
```

挂卷后：容器删了数据还在；练习库弄脏了再考虑 `-v` 重建。

### 4.5 环境受限时怎么办？

#### 为什么单独写一节？

练习验收允许「书面 + SQLite 近似」，但**概念不能跳**：

1. 仍要会写 PG 类型/约束的 SQL（可先不执行）  
2. 笔记标明：SQLite 无真正 `TIMESTAMPTZ` / 外键默认可能未开启等差异  
3. 有条件时再补一次 Docker 连通  

### 4.6 易错点

| 错法 | 会发生什么 |
|------|------------|
| 本机 5432 已被占用 | 端口冲突；改映射 `-p 5433:5432`，URL 端口跟着改 |
| 容器刚起立刻连 | 还在 init → 连接拒绝；等几秒或看 `docker logs` |
| 密码/库名和环境变量不一致 | `FATAL: password authentication failed` 或 database 不存在 |
| 把演示密码用于公网 | 安全事故；生产用强密码 + 密钥管理 |
| `docker rm` 却期望数据还在（未挂卷） | 数据没了——教学库可重建，重要数据先挂卷 |

### 4.7 对照：连接串里的主机名

| 你在哪跑应用 | `主机` 怎么填 |
|--------------|---------------|
| 本机 Python ↔ 本机映射端口的容器 | `localhost` / `127.0.0.1` |
| 同 compose 网络里的 API 容器 | 服务名，如 `db` |
| 云 RDS | 云控制台给的主机名 |

## 5. 必掌握：连接配置

服务起来只完成一半；应用侧要**稳定、可切换环境地**连上它。

### 5.1 为什么用环境变量而不是写死在代码里？

```text
本地 → localhost + 弱密码
预发 → 内网主机 + 另一套凭据
生产 → 托管实例 + 强密码 / IAM
```

写死 URL → 一次提交进 git 就等于泄露；换环境还要改代码。

### 5.2 怎么写：两种 URL（务必分清）

应用侧推荐环境变量：

```text
# SQLAlchemy 方言 URL（给 create_engine / create_async_engine 用）
DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/agent

# 裸 psycopg / 多数 GUI 常用（无 +psycopg 后缀）
# postgresql://user:pass@localhost:5432/agent
```

| URL | 给谁用 |
|-----|--------|
| `postgresql://...` | `psycopg.connect`、GUI、`psql` 思维 |
| `postgresql+psycopg://...` | **SQLAlchemy** 同步驱动标记 |
| `postgresql+asyncpg://...` | SQLAlchemy **异步**（下一章常见） |

原则：

- 密码不进仓库（进 `.env`，且 `.env` 进 `.gitignore`）  
- 区分本地/预发/生产 URL  
- 连接池由 ORM/驱动管理（下一章）  
- `+psycopg` 是 **SQLAlchemy** 驱动标记，不要原样塞进 `psycopg.connect()`

### 5.3 跑一下：最小 Python 连通（可选）

```bash
pip install psycopg[binary]
```

```python
# playground 里可自建探活脚本；勿提交真实密码
import os

import psycopg

url = os.environ["DATABASE_URL"]  # 使用裸 postgresql://...
# 若误设了 postgresql+psycopg://，这里先替换掉方言后缀再连
url = url.replace("postgresql+psycopg://", "postgresql://", 1)

with psycopg.connect(url) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT 1")
        print(cur.fetchone())  # (1,)
```

期望输出：`(1,)`。能打印出来，说明：**网络、账号、库名**三条都通了。

### 5.4 `.env` 习惯（和练习 B3 对齐）

```text
# .env（示例，勿提交）
POSTGRES_USER=postgres
POSTGRES_PASSWORD=postgres
POSTGRES_DB=agent
POSTGRES_HOST=localhost
POSTGRES_PORT=5432

# 也可以直接一整段：
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/agent
```

仓库里可放 `.env.example`（无真实密钥），写明变量名。

### 5.5 易错点

| 错法 | 会发生什么 |
|------|------------|
| 把 `postgresql+psycopg://` 传给 `psycopg.connect` | 解析失败或找不到驱动 |
| URL 里密码含 `@` `#` 等特殊字符未编码 | 主机/密码被截断解析错 |
| 提交 `.env` | 密钥泄露；立刻轮换密码 |
| 本地/CI/生产共用一个 URL | 互相污染数据；权限过大 |
| 忽略 SSL 要求（云库） | 连接被拒；云控制台通常要求 `sslmode` |

### 5.6 对照：配置项清单

| 项 | 示例 | 说明 |
|----|------|------|
| 用户 | `postgres` | 本地演示用户；生产最小权限账号 |
| 密码 | （密钥） | 环境变量 / 密钥管理 |
| 主机 | `localhost` | 见 §4.7 |
| 端口 | `5432` | 映射改了要同步 |
| 数据库 | `agent` | 与 `POSTGRES_DB` 一致 |
| 驱动标记 | `+psycopg` / `+asyncpg` | 仅 SQLAlchemy URL |

## 6. 建议掌握：JSONB 与迁移

关系列管「核心真相」；JSONB 管「形状还在变的扩展信息」。迁移管「表结构怎么安全进化」。

### 6.1 JSONB：为什么需要？

Agent 常见半结构化数据：

- 工具调用参数快照  
- 模型返回的扩展字段（`usage`、`raw`）  
- 前端实验旗帜、A/B 标记  

这些字段**每周都可能多键**，为每个键加正式列会把迁移打爆 → JSONB 合适。

但：**要 WHERE / JOIN / 强约束的核心字段，仍应正式列 + 索引。**

### 6.2 JSON vs JSONB（怎么选）

| | `JSON` | `JSONB` |
|--|--------|---------|
| 存储 | 文本，保输入空白 | 二进制，去重键、可索引 |
| 查询 | 较弱 | **推荐**；`->>`、GIN 等 |
| 本章默认 | — | **用 JSONB** |

### 6.3 怎么写：加列与查询

```sql
ALTER TABLE messages
  ADD COLUMN metadata JSONB NOT NULL DEFAULT '{}'::jsonb;

-- 写入
UPDATE messages
SET metadata = '{"model":"gpt-x","temperature":0.2}'::jsonb
WHERE id = 1;

-- 按键查询（->> 取出 text）
SELECT id, content
FROM messages
WHERE metadata->>'model' = 'gpt-x';
```

常用运算符直觉：

| 写法 | 含义 |
|------|------|
| `metadata->>'model'` | 取键 `model` 为 **文本** |
| `metadata->'model'` | 取键为 **JSON** |
| `metadata @> '{"model":"gpt-x"}'::jsonb` | 包含（常配合 GIN） |

适合：工具参数快照、模型返回的扩展字段。  
核心查询字段仍应用正式列 + 索引。

### 6.4 跑一下

```sql
ALTER TABLE messages
  ADD COLUMN IF NOT EXISTS metadata JSONB NOT NULL DEFAULT '{}'::jsonb;

INSERT INTO messages (session_id, role, content, metadata)
VALUES (
  '11111111-1111-1111-1111-111111111111',
  'assistant',
  'hi',
  '{"model":"echo","latency_ms":12}'::jsonb
);

SELECT id, metadata->>'model' AS model, metadata->>'latency_ms' AS latency
FROM messages
WHERE metadata->>'model' = 'echo';
```

高频键以后真要筛选，再考虑：

```sql
CREATE INDEX idx_messages_metadata_model
  ON messages ((metadata->>'model'));
-- 或 GIN：CREATE INDEX ON messages USING GIN (metadata);
```

### 6.5 JSONB 易错点

| 错法 | 会发生什么 |
|------|------------|
| 把 `user_id`、`role` 只放进 JSONB | 无 FK/CHECK；统计与关联变难 |
| 当完整文档库用，从不建关系表 | 失去 PG 最大优势 |
| 假设键一定存在 | `->>'x'` 对缺失键得 `NULL`；要想好默认 |
| 巨无 JSON 塞每一行 | 行宽膨胀；考虑外置对象存储 + 存引用 |

### 6.6 迁移思路：为什么不能「生产手工点」？

```text
改表不要只在生产手工点
→ 用迁移脚本（Alembic 等）版本化
→ 可上可回滚（尽量）
```

手工在 GUI 加点列的问题：

1. 本地 / 预发 / 生产结构漂移  
2. 无法 code review  
3. 出事不知如何复现  

### 6.7 怎么写：迁移五步心智（对齐练习 A2）

不必这章就装齐 Alembic，先背流程：

```text
1. 改模型 / 写 SQL 变更意图（加列、加索引、改约束）
2. 生成迁移脚本（Alembic revision --autogenerate 等）
3. 人读 upgrade/downgrade：禁止盲信自动生成
4. 先在本地 / CI 打到测试库
5. 再应用到预发 → 生产；记录版本（alembic_version）
```

最小命令地图（细节下一章）：

```bash
alembic revision --autogenerate -m "add messages.metadata"
# 审查生成的 upgrade/downgrade SQL
alembic upgrade head
```

下一章 ORM 会接到 Alembic。

### 6.8 跑一下（书面推演也算）

假设现状：`messages` 无 `metadata`。目标：全环境一致加上 JSONB 列。

| 环境 | 动作 |
|------|------|
| 开发 | 写迁移 → `upgrade head` → 插入测试行 |
| CI | 空库从零 `upgrade head`，跑测试 |
| 生产 | 备份策略就绪后执行同一版本迁移 |

回滚尽量有 `downgrade`；但**删列/改类型**的回滚可能丢数据——迁移设计时要想清楚。

### 6.9 迁移易错点

| 错法 | 会发生什么 |
|------|------------|
| 生产手工改、本地靠模型「感觉一致」 | 某天 ORM 映射对不上真实表 |
| 自动生成不看就提交 | 误删列、错类型、锁表语句 |
| 大表加列不评估锁/重写 | 高峰期阻塞写入（进阶话题） |
| 把数据修复 SQL 和结构迁移搅成一团 | 难回放；数据修复应可单独审计 |

### 6.10 对照：正式列 vs JSONB vs 迁移

| 数据 | 放哪 | 变更方式 |
|------|------|----------|
| `role`、`session_id`、`created_at` | 正式列 + 约束 | 迁移 |
| 偶发扩展键、模型 raw | JSONB | 键可先不加迁移；**列本身**仍要迁移加上 |
| 新核心筛选维度（如 `model` 总按它查） | 升级为正式列 | 迁移 + 回填 |

## 7. 了解即可：扩展与调优

本章目标是**地图**，不是让你立刻当 DBA。有慢查询、有向量检索需求时再深挖。

### 7.1 为什么先建立地图？

PG 很深：存储、vacuum、复制、扩展……过早钻进去会挤掉「能连上、能建表、能迁移」的主线。但完全不提，排障时你会不知道该搜什么词。

### 7.2 扩展（Extensions）直觉

```sql
-- 示例：启用扩展（权限与镜像预装情况因环境而异）
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- 模糊/相似搜索常见
-- CREATE EXTENSION IF NOT EXISTS vector; -- 向量（常见为 pgvector 镜像/打包）
```

和 Agent 相关的扩展方向（名字作地图即可）：

| 方向 | 用途 |
|------|------|
| 向量扩展生态 | embedding 近邻检索 |
| 全文检索 | 文档/消息搜索 |
| `pg_trgm` 等 | 模糊匹配 |

**了解即可**：知道「PG 靠扩展长能力」，具体安装跟镜像/托管文档走。

### 7.3 调优入口词

等你真的遇到慢查询，按这个顺序搜：

```text
EXPLAIN ANALYZE
→ 有没有合理索引
→ 连接数 / 池子是否打满
→ vacuum / 表膨胀
→ 再考虑硬件与副本
```

| 词 | 直觉 |
|----|------|
| `EXPLAIN ANALYZE` | 看计划：顺序扫还是走索引 |
| 连接数 | 每个 App 副本 × 池大小 < 库 `max_connections` 预算 |
| vacuum | 回收死元组；自治有 autovacuum |
| 索引 | 加速读、拖慢写；与上一章索引直觉相同 |

### 7.4 易错点（了解级）

| 错法 | 会发生什么 |
|------|------------|
| 一上来就乱改 `postgresql.conf` | 无基线；更难排障 |
| 每个微服务开很大的连接池 | 打满连接；新请求排队/失败 |
| 把向量检索当「银弹」却不设计元数据表 | 过滤、权限、审计仍然要关系列 |

### 7.5 对照：本章边界

| 现在就要会 | 以后再学 |
|------------|----------|
| 类型、约束、Docker 连通、URL | 复制、分区、深度调参 |
| JSONB 边界、迁移心智 | 零停机迁移套路 |
| 知道 `EXPLAIN` / 扩展存在 | 专项性能与向量方案 |

`EXPLAIN ANALYZE`、连接数、vacuum、向量扩展……等有慢查询再深入。
