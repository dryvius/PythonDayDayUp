## 1. 为什么要学（和 Agent 的关系）

Agent 运行时典型画像：

```text
等 LLM HTTP 响应（网络 I/O）
等数据库 / 向量库（网络 I/O）
本地解析 JSON、拼 prompt（少量 CPU）
写日志、读文件（磁盘 I/O）
```

大多数时间在 **等 I/O**，不是在算矩阵。  
所以你会听到：异步、超时、连接池、文件句柄耗尽——都建立在 OS 概念上。

## 2. 必掌握：进程与线程

### 2.1 进程（Process）

- 操作系统调度的**资源容器**：独立内存地址空间
- 一个 Python 解释器进程默认很常见
- 进程间默认内存隔离，通信要管道/队列/网络

### 2.2 线程（Thread）

- 进程内的**执行流**
- 同进程线程共享内存（也共享坑：竞态）
- 一个进程可有多线程

### 2.3 对照（前端直觉）

| 概念 | 可粗对照 |
|------|----------|
| 浏览器进程 | 独立标签/站点隔离 |
| JS 主线程 | 单线程事件循环（更像“一个执行流 + 异步 I/O”） |
| Web Worker | 类似额外线程，但不共享随意内存 |

Python 还有 **GIL**（见本模块 [`03-concurrency-models.md`](./03-concurrency-models.md)）：多线程对 CPU 密集帮助有限，对 I/O 等待仍有用。

### 2.4 小实验直觉

```python
import os
from pathlib import Path

print("pid=", os.getpid())
print("cwd=", Path.cwd())
```

每次运行都是一个进程；`pid` 会变。

## 3. 必掌握：内存与 I/O

### 3.1 内存

- 进程拿到的是虚拟内存视图；物理页由 OS 管理
- Python 对象在堆上，有开销；大 list / 大上下文会吃内存
- Agent 常见内存压力：消息历史过长、一次加载过大语料、向量全进内存

实践：

```text
上下文截断、流式处理、分页读取、不要 list(巨大生成器)
```

### 3.2 I/O

| 类型 | 例子 | Agent 里 |
|------|------|----------|
| 网络 I/O | HTTP 调 LLM | 最常见瓶颈 |
| 磁盘 I/O | 读文档、写日志 | RAG 建库、会话落盘 |
| 终端 I/O | print | 调试 |

**阻塞 I/O**：调用发出去，线程在等结果回来之前干不了别的（除非用多线程/异步换出）。

## 4. 必掌握：文件描述符直觉

在 Unix-like 上，打开的文件、socket 都对应一个 **fd（文件描述符）** 整数。  
Windows 是句柄（handle）概念，思想类似：**打开的东西占名额**。

后果：

- 打开文件忘记关 → 泄漏
- 连接不复用、不关闭 → 可能触达上限（`Too many open files`）
- 所以要用 `with open`、连接池、异步客户端正确关闭

```python
from pathlib import Path

path = Path("demo.txt")
with path.open("w", encoding="utf-8") as f:
    f.write("ok")
# 离开 with：关闭，归还句柄
```

## 5. 建议掌握：调度与阻塞

### 5.1 调度

CPU 核有限，OS 在很多可运行线程间切换（时间片）。  
你的程序“同时跑”常常是**交错执行**。

### 5.2 阻塞 vs 睡眠 vs 忙等

- **阻塞**：等 I/O，线程暂时不占 CPU 做事
- **sleep**：主动让出一段时间
- **忙等**：空转耗 CPU（通常糟糕）

Agent 超时设置本质是：我不想无限阻塞在一次 LLM 调用上。

## 6. 了解即可：内核细节

系统调用、页表、中断、调度器算法——知道存在即可。  
排障时用到再查。

## 7. 常见坑

1. 把“电脑卡”全怪 Python，其实可能是同步串行等网络
2. 无限追加 history 导致内存涨
3. 高并发下耗尽 fd/连接数
4. 在 CPU 密集任务上死磕多线程（见《并发模型》章的 GIL）
