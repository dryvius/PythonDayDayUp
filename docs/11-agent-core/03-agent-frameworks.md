## 本章定位

- **模块目标**：理解 Agent 本质，能手写并使用框架构建 Agent。
- **本章角色**：理解框架解决什么、何时不用；建立读源码切入点与选型地图。
- **原则**：框架是加速器，不是理解的替代品。先手写循环再用框架。
- **前置**：上一章的 tool-loop、状态机、`max_steps`、轨迹与 FakeLLM；下一章会用「图」把分支与 checkpoint 做细。
- **一句话**：框架帮你少写胶水；产品逻辑、权限、评测、成本、失败策略仍是你的。

## 学习目标（学完应能做到）

1. 列出框架通常封装的能力，并分清「省掉的样板」与「仍须自己负责」。
2. 能判断项目何时不该上框架、何时值得上。
3. 知道读 Agent 框架源码从哪几层看，带着问题对照手写实现。
4. 能做「可控性 / 生态 / 绑定度」级选型讨论（重思想，不绑死品牌）。
5. 能对「自研薄封装 / 全量框架 / 中间态只借用一层」给出理由。

## 重点分级

| 级别 | 内容 | 要求 |
|------|------|------|
| **必掌握** | 框架价值、何时不用、源码切入点 | 能决策；能读一层源码 |

## 1. 框架通常解决什么

这一节会刻意写细——后面「用/不用」「读源码」「选型」都建立在「框架到底替你管了什么」之上。

### 1.1 为什么需要「Agent 框架」这一层？

#### 为什么不能永远只靠手写 for 循环？

上一章你已经能手写：

```text
messages → LLM(+tools) → 有 tool_calls？→ 执行 → 写回 → 再调 LLM → …
```

这条主链足够学本质。一旦项目要同时处理：

```text
多厂商消息 / tool schema 差异
分支、重试、人工确认、长任务暂停恢复
记忆切片、checkpoint、会话恢复
统一 tracing / 回调 / 评测钩子
RAG 检索器、向量库、文档加载器拼装
多 Agent 角色与通讯拓扑
```

你会反复写**同一类胶水**：适配器、序列化、状态合并、插件注册。框架的价值不是「更聪明的 Agent」，而是把这些样板收成可复用层。

#### 怎么理解（两张责任表）

框架通常封装（省样板）：

```text
消息与工具 schema 适配多厂商
运行循环 / 图编排
记忆与 checkpoint
tracing / 回调
RAG 组件拼装
多 Agent 通讯模式
```

你仍要负责（省不掉）：

```text
产品逻辑与提示纪律
权限 / ACL / 租户隔离
评测集与回归
成本与限流
失败策略与降级
业务侧状态语义（「订单已确认」比「step=3」重要）
```

心智一句：

> 你省下的是样板代码；你仍要负责：产品逻辑、权限、评测、成本、失败策略。

#### 清单：框架六块能力分别解决什么疼

| 能力块 | 没有它时你要手写什么 | 它真正省下的 |
|--------|----------------------|--------------|
| 消息 / Tool schema 适配 | 各厂商 `tool_calls` 字段、流式增量、并行工具结果回写 | 换模型时少改业务 |
| 运行循环 / 图编排 | `for` + `if` 路由、终止、人机节点 | 复杂控制流显式化 |
| 记忆与 checkpoint | 会话截断、摘要、磁盘/DB 快照、恢复点 | 长任务可暂停、可重放 |
| tracing / 回调 | 逐步打点、token、延迟、错误分类 | 可观测与评测挂钩 |
| RAG 拼装 | loader → chunk → index → retrieve → prompt | 数据侧组件可插拔 |
| 多 Agent 通讯 | 角色、邮箱/黑板、交接协议 | 拓扑可配置（别默认上） |

#### 易错点

| 错法 | 会发生什么 |
|------|------------|
| 以为上了框架 Agent「更准」 | 准确度仍靠工具设计、检索、提示与评测；框架不替你想业务 |
| 把框架当黑盒，只抄 Quickstart | 一旦异常停在框架内部，你无法定位是路由、adapter 还是工具层 |
| 用框架堆功能代替画状态机 | 分支一多，配置比代码更难读；本质状态仍要你说清 |
| 把「生态大」当成「适合我」 | 组件多 ≠ 你的控制流需要那么多；绑定成本后置爆发 |

#### 对照：手写 Agent vs 框架

```text
手写：看清状态、工具、终止、错误
框架：少写胶水，换来版本与抽象成本
```

| 维度 | 手写 tool-loop | 典型 Agent 框架 |
|------|----------------|-----------------|
| 状态在哪 | 你的 `messages` / `status` 字段 | 框架 State / Graph state / Session |
| 终止谁说了算 | 你的 `max_steps` / 熔断 | 配置 + 内部 executor 策略（须核对） |
| 换厂商 | 改你的 adapter | 理想情况只换 model 配置 |
| 升级成本 | 低（代码你熟） | 中～高（抽象与 break 变更） |
| 学习曲线 | 先陡后稳 | 文档快，调试框架内部更陡 |

### 1.2 怎么理解「封装」：不是魔法，是分层

#### 为什么要分层看？

否则你会把「厂商 SDK」「编排引擎」「RAG 套件」「可观测插件」混成一团，选型时无法拆开买、拆开弃。

#### 怎么理解（五层栈）

从上到下（越往下越靠近基础设施）：

```text
5) 产品与策略层     —— 你的业务规则、ACL、评测、成本预算   ← 几乎总是自研
4) 编排层           —— loop / graph / workflow / 人机节点
3) 能力拼装层       —— tools 注册、memory、RAG、多 Agent 拓扑
2) 模型适配层       —— messages / tool_calls / streaming 转换
1) 运行时与观测层   —— 执行、重试、callback、trace export
```

多数「Agent 框架」横跨 2～4 层；有的强在 3（数据/RAG），有的强在 4（图编排）。  
**厂商 Agent SDK** 往往把 2 做得很顺，但 4/5 容易把你锁进其生态。

#### 示例：同一能力在手写与框架中的「等价物」

| 你在手写里已有的 | 框架里常见名字（会变，抓角色） |
|------------------|--------------------------------|
| `messages: list[dict]` | ChatMessage / MessageGraph / state["messages"] |
| `for step in range(max_steps)` | AgentExecutor / graph compile + invoke |
| `run_tool_call(...)` | ToolNode / tool runtime / function calling bridge |
| `trace.append(...)` | CallbackHandler / tracer / run tree |
| 会话存盘（若你做了） | Checkpointer / MemorySaver / session store |

读源码时，用上表当「寻宝图」，比通读营销文档快。

#### 易错点

- 把第 5 层（产品策略）塞进框架配置文件 → 权限与业务规则散落，审计困难。
- 只学第 3 层组件名，不理解第 4 层控制流 → 会拼玩具，不会做可恢复工作流。

#### 对照：和「Web 框架」类比

| Web | Agent |
|-----|--------|
| 路由 / 中间件 | 编排 / 回调链 |
| ORM / 驱动适配 | 模型 adapter / 向量库适配 |
| 你仍要写业务 Service | 你仍要写工具语义与失败策略 |
| 不会因为用了框架就自动安全 | 不会因为用了框架就自动可控 |

## 2. 必掌握：何时不用 / 何时用

这一节是决策章——学完应能对具体场景给出「用/不用」理由，而不是「别人都在用所以用」。

### 2.1 为什么「先不用」往往是正确默认？

#### 为什么本路线要求先手写？

因为框架会**藏状态机**。若你还说不清：

```text
工具结果怎样写回 messages？
最大步数在哪强制停止？
失败工具会不会静默吞掉？
重复 tool_call 会不会烧钱打转？
```

上框架只会把问题从「我的 for 循环」挪到「框架内部某处」，调试更贵。

#### 怎么理解（决策轴）

用三轴判断，而不是用星数：

```text
控制流复杂度：线性三步  ←→  图状分支 + 人机 + 长暂停
团队熟悉度：    无人熟框架 ←→  有人能 debug 框架内部
绑定容忍度：    必须极强可控 ←→  可接受抽象与升级成本
```

决策一句（务必记住）：

> 若你说不清框架替你管了哪段状态机，就还不到上框架的时候。

### 2.2 清单：先不用

| 场景 | 为什么先不用 |
|------|----------------|
| 学习阶段把本质走通（本路线要求） | 目标是内化 tool-loop，不是堆依赖 |
| 单次 tool call 或线性三步以内 | 手写更短、更透明；框架启动成本不划算 |
| 框架版本剧烈变动、团队无人熟悉 | 升级与排障会吞噬交付时间 |
| 需要极强可控的状态机，框架魔法过重 | 合规/风控路径必须逐步可审计 |
| 核心路径必须可单测且确定性高 | FakeLLM + 自研 loop 往往比框架夹具更稳 |

补充信号（出现任意两条就谨慎）：

- 你无法画出「等价于手写 Agent 的状态图」
- README 的 Quickstart 跑通了，但你解释不清一次 invoke 的调用栈
- 业务里已经出现「为了迁就框架 API 而扭曲领域模型」

### 2.3 清单：可以上

| 场景 | 框架真正买到的 |
|------|----------------|
| 图状分支、人工确认、持久化执行、长时间暂停恢复 | 编排 + checkpoint，而不是再造工作流引擎 |
| 多供应商适配成本高 | 模型/消息 adapter 层 |
| 团队需要统一脚手架与可观测插件 | 约定、回调、trace 出口一致 |
| 要快速试很多集成（搜索、向量库、tracing SaaS） | 生态连接器（注意绑定） |
| 多个项目要共享同一套 Agent 运行时 |「公司内平台」比「每个服务手写一套」划算 |

### 2.4 示例：三场景快速判决（练习预热）

| 场景 | 建议 | 理由（要点） |
|------|------|----------------|
| 内部小工具：查天气 + 算数，日调用量低 | **不用**重框架 | 线性 tool-loop；手写 + 日志足够 |
| 客服助手：检索知识库 → 可能转人工审批退款 | **考虑**图/工作流向框架或自研图执行器 | 有分支与人机节点；需要可暂停 |
| 强合规交易指令：每一步工具调用要过 ACL 与双人复核 | **自研薄封装**或框架但**自管状态机** | 可控性优先；别让魔法路由绕过审计 |

#### 易错点

| 错法 | 纠正 |
|------|------|
| 「以后可能会复杂，先上大框架」 | 用复杂度**现状**决策；预留接口比预装全家桶便宜 |
| 「不用框架就不专业」 | 能说清状态机与评测的团队，比会抄模板的团队专业 |
| 「用了框架就不能自研」 | 常见中间态：自研 loop + 只借用消息类型或 tracing（见 §5） |
| 把「能跑 Demo」当成「能上生产」 | 生产还缺：权限、预算、评测回归、失败降级（模块 12） |

#### 对照：用/不用一句话板

```text
控制流简单 + 要学本质     → 不用
控制流简单 + 要交付快     → 薄封装或轻量 SDK，仍可不引入重编排
控制流复杂 + 要暂停恢复   → 上编排（框架或自研微型图）
合规极强 + 必须逐步审计   → 自研或框架「可插拔执行器」，状态机自己握
```

## 3. 必掌握：阅读源码的切入点

框架文档会过时；**分层读源码**的习惯不过时。目标不是读完整个仓库，而是在 1～2 小时内找到与手写 Agent 的等价物。

### 3.1 为什么要从这几层看？

#### 为什么不能从 examples/ 开始通读？

Examples 展示「幸福路径」。生产事故多在：

```text
工具失败如何写回？
并行 tool_calls 顺序？
max_iterations 是否真的硬停？
checkpoint 恢复后会不会重复执行副作用？
```

这些答案在**数据结构与执行器**里，不在博客标题里。

#### 怎么理解（五层切入点）

按层看（与 §1.2 对齐）：

```text
1) 消息与 Tool 数据结构
2) Agent / Executor 主循环 或 Graph compile
3) Model adapter（如何转 tool_calls）
4) Memory / Checkpointer
5) Callback / Tracing
```

建议阅读顺序：`1 → 2 → 3`，然后按你项目痛点补 `4` 或 `5`。  
多 Agent 与 RAG 拼装可后看——它们建立在前三层之上。

### 3.2 每层看什么：问题清单

#### 1) 消息与 Tool 数据结构

带着问题：

- `role` 有哪些？`tool` 结果挂在哪几个字段？
- 一次 assistant 能否同时有 `content` 与多个 `tool_calls`？
- 工具参数是 `str`（JSON 文本）还是已解析 `dict`？谁负责校验？

搜索关键词（跨仓库通用）：

```text
ToolMessage / FunctionMessage / tool_calls
BaseMessage / ChatMessage
tool_call_id / tool_call_id
```

#### 2) Agent / Executor 主循环 或 Graph compile

带着问题：

- 最大步数 / 迭代在哪强制停止？
- 无 `tool_calls` 时如何判定 DONE？
- 异常是抛出、写入状态，还是被回调吞掉？

搜索关键词：

```text
AgentExecutor / ainvoke / invoke
should_continue / route / add_conditional_edges
max_iterations / recursion_limit
```

#### 3) Model adapter

带着问题：

- 厂商 A 的流式 `tool_calls` 增量如何拼成一次完整调用？
- 换模型时，业务节点要不要改？

搜索关键词：

```text
bind_tools / with_structured_output
_convert_ / to_openai / tool_choice
```

#### 4) Memory / Checkpointer

带着问题：

- checkpoint 存的是「消息全文」还是「状态快照」？
- 恢复后副作用节点（发邮件、扣款）有没有幂等键？

搜索关键词：

```text
checkpointer / MemorySaver / put / get_tuple
thread_id / checkpoint_id
```

#### 5) Callback / Tracing

带着问题：

- 能否在不改业务节点的情况下挂钩子？
- 默认会不会把完整 prompt 打到外部 SaaS？（合规）

搜索关键词：

```text
CallbackManager / on_tool_start / on_llm_end
trace / span / run_id
```

### 3.3 示例：对照手写实现的「寻宝」流程

假设你上一章有：

```python
for step in range(1, self.max_steps + 1):
    assistant = self.llm.complete(self.messages, tools=tool_defs)
    self.messages.append(assistant)
    tool_calls = assistant.get("tool_calls") or []
    if not tool_calls:
        return assistant.get("content") or ""
    for call in tool_calls:
        self.messages.append(run_tool_call(call, self.tools))
```

读任意框架时，逐项找等价物：

| 手写片段 | 到框架里找 |
|----------|------------|
| `self.messages.append(assistant)` | 状态 reducer / message list 追加逻辑 |
| `tool_calls = ... or []` | 解析 assistant 的适配代码 |
| `run_tool_call` | ToolNode / tool executor |
| `range(1, max_steps+1)` | recursion_limit / max_iterations |
| `trace.append` | callback / tracer 事件 |

#### 带着总问题读（抄到便签上）

> 工具结果怎样写回 messages？最大步数在哪强制停止？失败工具会不会静默吞掉？

对照你的手写实现逐项找「等价物」，比通读文档更快。

### 3.4 易错点与阅读纪律

| 错法 | 更好的做法 |
|------|------------|
| 从最新 blog 追 API 名 | 先锁定「层」，再搜符号 |
| 一上来读多 Agent 示例 | 单 Agent 执行器未懂前，拓扑只会更迷 |
| 只看类型注解不看分支 | `if error` / `except` 路径才是生产行为 |
| 改源码打补丁当长期方案 | 能 hook 就 hook；要 fork 先评估升级成本 |
| 以为读完 README 等于会维护 | 至少跟一次失败工具的调用栈 |

#### 对照：读框架 vs 读你自己的 Agent

| | 读手写 Agent | 读框架 |
|--|--------------|--------|
| 入口 | `Agent.run` | `invoke` / `compile().invoke` / CLI |
| 状态 | dataclass 字段 | State schema / channel / checkpoint |
| 停机 | 你写的 return | 配置项 + 内部 break 条件（必须核实） |
| 目标 | 实现正确 | **映射等价物 + 找隐藏策略** |

## 4. 建议掌握：对比维度（重思想，不绑死品牌）

选型看表，不看星数。品牌三个月一变；**问题清单**可以沿用多年。

### 4.1 为什么要「维度」而不是「排行榜」？

#### 为什么榜单会害人？

榜单优化的是曝光与生态叙事；你的约束是：可控性、合规、团队能力、绑定成本。  
同一团队在「内部工具」与「受监管工作流」上，最优解可以完全不同。

#### 怎么理解（先问问题，再贴标签）

| 维度 | 你要问的问题 |
|------|----------------|
| 编排模型 | 线性 loop / 图 / 工作流引擎？ |
| 可控性 | 状态能否自己定义？能否插入 ACL？ |
| 可观测 | 原生 trace / 回调是否好用？ |
| 模型适配 | 换厂商是否改业务代码？ |
| 数据/RAG | 是否强绑某一套索引？ |
| 绑定成本 | 升级是否经常 break？文档是否跟得上？ |
| 团队 | 有人能 debug 框架内部吗？ |

### 4.2 每个维度怎么打分（实用尺度）

不必 1～10 分；用三级即可：`弱 / 中 / 强`（相对你的场景）。

#### 编排模型

```text
弱：只提供「单次 LLM + tools」助手 API
中：有 loop，条件分支要自己写大量 if
强：一等公民的图/工作流、人机节点、可暂停
```

问自己：我的控制流是「一条路走到底」还是「多出口状态机」？

#### 可控性

```text
弱：业务状态藏在框架对象里，难插入 ACL
中：能挂前置/后置钩子，状态字段可扩展
强：状态 schema 自管；每跳工具执行可替换为自有 runner
```

强合规场景把「可控性」权重拉满。

#### 可观测

```text
弱：只能 print / 无统一 run_id
中：有 callback，字段要自己规范
强：span 树清晰，易导出到现有 APM；默认不泄密
```

与模块 12 的字段允许列表对齐——框架默认太吵或太露也不合格。

#### 模型适配

```text
弱：示例只通一家；换厂商要改节点代码
中：有 adapter，边缘模型要自己补
强：业务节点只认「消息 + tools」抽象
```

#### 数据 / RAG

```text
弱：几乎不管检索
中：有连接器，索引生命周期你自管更稳
强：数据管线完整——但也更易绑死索引假设
```

RAG 很重时，问：能否只用它的 retriever 接口，编排仍自研？

#### 绑定成本

```text
弱绑定：核心是你的状态机；框架可替换
中：用了其 State / Message 类型，迁移要写转换层
强绑定：业务散落在其 DSL / 特有装饰器 / 云端专有运行时
```

#### 团队

再强的框架，若无人能读 §3 那五层，生产事故会变成「等上游 issue」。

### 4.3 粗地图（会变，只作直觉）

下列名称**只作方向直觉**，不是推荐榜；API 与定位会变。学会 §4.1 的问题后，你可以自己更新这张表。

| 方向 | 直觉 |
|------|------|
| LangChain / LangGraph | 组件多；图编排与生态大 |
| LlamaIndex | 数据/RAG 侧强 |
| 轻量 Agent SDK / 自研 | 可控、薄、要自己补齐 |
| 厂商 Agent SDK | 集成快、易绑定生态 |

**会手写 tool loop 后**，学任何框架都更快——因为你在找等价物，而不是背 API。

### 4.4 示例：用维度做一次「纸上选型」

场景：要做「检索 → 起草工单 → 人工确认 → 执行变更」，模型可能换供应商。

| 维度 | 需求 | 对方向的含义 |
|------|------|----------------|
| 编排 | 需要人机 + 暂停 | 偏向图/工作流，而非纯 chat SDK |
| 可控 | 执行变更前必须 ACL | 工具执行器最好可替换 |
| 模型适配 | 可能换厂商 | 业务节点勿直接依赖某一家 request 形状 |
| RAG | 中等 | 可用独立检索服务，不必强绑同一全家桶 |
| 团队 | 2 人后端 | 选「能读源码的薄层」或「一人已熟的图库」 |

结论形态应是：「选 X 方向，因为编排+可控；避开 Y，因为强绑云端运行时」——而不是「选最火的那个」。

#### 易错点

| 错法 | 纠正 |
|------|------|
| 用 GitHub stars 代替维度表 | stars ≠ 适合你的控制流与合规 |
| 为 RAG 选了编排很重的栈 | 可以组合：检索一套、编排另一套或自研 |
| 忽视升级 break | 先看 changelog 节奏与你的评测能否拦住 |
| 把「教程多」当成「好维护」 | 教程多往往伴随抽象层多；维护看源码可读性 |

#### 对照：思想层 vs 品牌层

| 思想层（应掌握） | 品牌层（会变） |
|------------------|----------------|
| loop / graph / workflow | 具体库名与装饰器 |
| messages + tool_calls 协议 | 某云「Agents」产品名 |
| checkpoint / 人机节点 | 某框架类名 |
| callback / trace 字段纪律 | 某 SaaS 控制台 |

## 5. 建议掌握：自研 vs 框架清单

决策不是二元开关。常见是**中间态**：自研 loop，只借用框架的某一层。

### 5.1 为什么要显式列出「适合自研」？

#### 为什么「能用框架」不等于「应该用框架」？

框架带来的不只是速度，还有：

```text
抽象泄漏（错误在框架深处）
版本耦合（升级打断业务）
技能门槛（新人先学框架方言）
过度拼装（为用而用组件）
```

当工具少、流程直、安全要求高时，自研薄封装的**总拥有成本**常常更低。

#### 怎么理解（三种姿态）

```text
A. 自研薄封装     —— 自有 Agent.run + 少量 adapter
B. 框架为主       —— 编排/记忆/观测都走框架
C. 中间态         —— 自研 loop + 只借用一层（消息类型 / tracing / 某一检索器）
```

默认从 A 或 C 长出来；证明 B 的复杂度被需要时再进 B。

### 5.2 清单：适合自研薄封装

- 工具 ≤10、流程以 loop 为主
- 强安全/合规，必须自己审每一跳
- 已有统一后端脚手架（日志、鉴权、配置、CI）可挂 Agent
- 团队更熟业务代码，不熟某框架方言
- 需要 FakeLLM / 契约测试极度稳定（夹具自己写更干净）

薄封装最小集合（对照上一章）：

```text
Agent.run / max_steps / 重复调用熔断
tool registry + ACL
model adapter（一家也可，接口留好）
trace 事件（给模块 12）
```

### 5.3 清单：适合框架

- 要 checkpoint、人机协同、复杂分支
- 快速试很多集成（搜索、向量库、tracing SaaS）
- 多项目要统一 Agent 运行时与观测出口
- 明确需要图可视化/持久化执行语义，自研成本高于学习框架

上框架时仍建议保留：

```text
业务工具函数纯净（可单测）
ACL 在工具执行前（不要只靠提示词）
评测回归集（升级框架先跑）
对「停止条件」的显式测试
```

### 5.4 中间态：只借用一层（推荐练习）

| 借用层 | 典型动机 | 风险 |
|--------|----------|------|
| 仅消息 / Tool 类型 | 少写 schema，执行器自研 | 类型升级仍可能牵连 |
| 仅 tracing / callback | 统一观测，编排自研 | SaaS 泄密与采样要自管 |
| 仅 retriever / 向量连接器 | RAG 组件成熟，Agent 自研 | 索引假设泄漏进业务 |
| 仅 graph 执行器 | 要分支/人机，其它自管 | 要学会其 state reducer |

原则：

> 借用「你愿意被绑的那一层」；核心状态机尽量留在自己仓库语义清晰的模块里。

### 5.5 示例：迁移六步（自研 → 某框架时）

不必现在就迁；先会排步骤：

1. **冻结行为**：用 FakeLLM 固化「闲聊不调工具 / 算数走工具 / 触顶停止」等用例。  
2. **画出状态机**：标出 DONE / FAILED / 人机等待。  
3. **映射等价物**：messages、tool runner、max_steps、trace。  
4. **先迁适配层**：模型 in/out 与工具 schema，业务工具函数先不动。  
5. **再迁编排**：loop → executor/graph；保留相同评测。  
6. **最后接记忆/观测插件**：确认脱敏与字段允许列表。

#### 易错点

| 错法 | 纠正 |
|------|------|
| 先改业务提示词再迁框架 | 先锁评测与状态机，再换执行器 |
| 把 ACL 交给「框架工具自动描述」 | ACL 是服务端强制，不是模型礼貌 |
| 中间态变成「两套状态真相」 | 选定一个 source of truth：你的 State 或框架 State |
| 为了用齐生态而引入用不到的组件 | 组件是负债；默认不装 |

#### 对照：成本账（定性）

| | 自研薄封装 | 重框架 |
|--|------------|--------|
| 前期速度 | 慢一点（你在学本质） | Demo 快 |
| 中期排障 | 快（代码在自己仓） | 取决于是否会读源码 |
| 合规审计 | 天然清晰 | 要额外证明框架路径 |
| 换框架/换厂商 | 接口在自己手里 | 看绑定层选得深不深 |
| 复杂工作流 | 要自建图或引入编排 | 往往现成 |

## 6. 了解即可：追新

### 6.1 为什么生态「三个月一变」仍不用焦虑？

#### 为什么 API 名次要？

因为不变的是思想件：

```text
状态、工具、记忆、图、评测
```

品牌、类名、云产品包装会换；你若抓住 §1～§5 的问题清单，任何新框架都是「再找一遍等价物」。

#### 怎么理解（更新节奏）

```text
每周：扫一眼你已用框架的安全通告 / break 变更（若已上生产）
每月：看思想层有没有新模式（如更主流的人机节点、更好的 trace 语义）
每季：用你的评测集回归；决定是否跟版本
```

不要：

```text
每个新库都重写业务
为追 Twitter 热帖引入第二套编排
在学习阶段并行深挖三个全家桶
```

### 6.2 清单：升级框架前

- 跑你的评测回归集（模块 12）
- 核对：max 步数、工具失败写回、checkpoint 恢复是否行为变化
- 读一遍 changelog 里与 `tool` / `message` / `checkpoint` 相关的条目
- 确认观测字段与脱敏策略未被默认「变啰嗦」

### 6.3 易错点

| 错法 | 纠正 |
|------|------|
| 追新当学习主线 | 主线仍是手写 loop → 再框架 → 再图（本模块顺序） |
| 把「新抽象」当成「新能力」 | 先问：它解决的是编排、适配，还是只是换皮 API |
| 无评测升级 | 升级 = 变更；无回归等于蒙眼发车 |

#### 对照：关注点

| 更值得关注 | 可以后看 |
|------------|----------|
| 状态与终止语义是否清晰 | 某个新 Demo 用了哪家模型 |
| 工具错误是否结构化回传 | 又一个包装同一 loop 的库 |
| 绑定层深浅 | 排行榜名次 |

生态三个月一变属常态。关注思想：状态、工具、记忆、图、评测；API 名次要。  
升级框架前先跑你的评测回归集（模块 12）。
