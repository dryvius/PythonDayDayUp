## 本章定位

- **本章角色**：理解框架解决什么、何时不用；建立读源码切入点与选型地图。
- **原则**：框架是加速器，不是理解的替代品。先手写循环再用框架。

## 学习目标

1. 列出框架通常封装的能力。
2. 能判断项目何时不该上框架。
3. 知道读 Agent 框架源码从哪几层看。
4. 能做「可控性 / 生态 / 绑定度」级选型讨论。

## 重点分级

| 级别 | 内容 | 要求 |
|------|------|------|

## 1. 框架通常解决什么

```text
消息与工具 schema 适配多厂商
运行循环 / 图编排
记忆与 checkpoint
tracing / 回调
RAG 组件拼装
多 Agent 通讯模式
```

你省下的是样板代码；你仍要负责：产品逻辑、权限、评测、成本、失败策略。

手写 Agent 与框架的关系：

```text
手写：看清状态、工具、终止、错误
框架：少写胶水，换来版本与抽象成本
```

---

## 2. 必掌握：何时不用 / 何时用

**先不用：**

- 学习阶段把本质走通（本路线要求）
- 单次 tool call 或线性三步以内
- 框架版本剧烈变动、团队无人熟悉
- 需要极强可控的状态机，框架魔法过重

**可以上：**

- 图状分支、人工确认、持久化执行、长时间暂停恢复
- 多供应商适配成本高
- 团队需要统一脚手架与可观测插件

决策一句：

> 若你说不清框架替你管了哪段状态机，就还不到上框架的时候。

---

## 3. 必掌握：阅读源码的切入点

按层看：

```text
1) 消息与 Tool 数据结构
2) Agent / Executor 主循环 或 Graph compile
3) Model adapter（如何转 tool_calls）
4) Memory / Checkpointer
5) Callback / Tracing
```

带着问题读：

> 工具结果怎样写回 messages？最大步数在哪强制停止？失败工具会不会静默吞掉？

对照你的手写实现逐项找「等价物」，比通读文档更快。

---

## 4. 建议掌握：对比维度（重思想，不绑死品牌）

| 维度 | 你要问的问题 |
|------|----------------|
| 编排模型 | 线性 loop / 图 / 工作流引擎？ |
| 可控性 | 状态能否自己定义？能否插入 ACL？ |
| 可观测 | 原生 trace / 回调是否好用？ |
| 模型适配 | 换厂商是否改业务代码？ |
| 数据/RAG | 是否强绑某一套索引？ |
| 绑定成本 | 升级是否经常 break？文档是否跟得上？ |
| 团队 | 有人能 debug 框架内部吗？ |

粗地图（会变，只作直觉）：

| 方向 | 直觉 |
|------|------|
| LangChain / LangGraph | 组件多；图编排与生态大 |
| LlamaIndex | 数据/RAG 侧强 |
| 轻量 Agent SDK / 自研 | 可控、薄、要自己补齐 |
| 厂商 Agent SDK | 集成快、易绑定生态 |

选型看表，不看星数。**会手写 tool loop 后**，学任何框架都更快。

---

## 5. 建议掌握：自研 vs 框架清单

适合自研薄封装：

- 工具 ≤10、流程以 loop 为主
- 强安全/合规，必须自己审每一跳
- 已有统一后端脚手架

适合框架：

- 要 checkpoint、人机协同、复杂分支
- 快速试很多集成（搜索、向量库、tracing SaaS）

中间态：自研 loop + 只借用框架的某一层（如仅用消息类型或仅用 tracing）。

---

## 6. 了解即可：追新

生态三个月一变属常态。关注思想：状态、工具、记忆、图、评测；API 名次要。  
升级框架前先跑你的评测回归集（模块 12）。
